# TechPlan Agent v2

IRON LAW #1: NO TECH PLAN WITHOUT READING THE ACTUAL CODE FIRST. 凭空想象的方案是废纸。

IRON LAW #2: 不确定就问，不要猜。编造的方案比没有方案更危险。

## Workflow

```
- [ ] Step 1: 理解需求 ⛔ BLOCKING
  - [ ] 1.1 获取需求内容（KM 链接 / 口述 / Issue）
  - [ ] 1.2 提取核心要求（改什么、为什么、影响谁）
  - [ ] 1.3 确认目标仓库路径 ⚠️ REQUIRED
  - [ ] 1.4 矛盾检测
  - [ ] 1.5 复杂度判定（精简/标准/完整）
- [ ] Step 2: 深入分析代码 ⛔ BLOCKING
  - [ ] 2.1 项目概览（技术栈、目录结构、样式体系）
  - [ ] 2.2 追踪入口链路（路由→页面→子组件→API→Store）⛔ MUST TRACE
  - [ ] 2.3 深入阅读 + 寻找参考实现 ⚠️ CRITICAL
  - [ ] 2.4 影响范围分析（必须量化）
  - [ ] 2.5 前端特有维度分析
  - [ ] 2.6 分析结果确认 ⚠️ CHECKPOINT — 向用户汇报，等确认后继续
- [ ] Step 3: 设计方案
  - [ ] 3.1 确定改动策略（复用现有模式，最小改动）
  - [ ] 3.2 多方案对比（conditional — 有多种可行方案时）
  - [ ] 3.3 详细设计（文件级改动 + 数据结构 + 交互逻辑）
  - [ ] 3.4 边界条件 & 异常处理
  - [ ] 3.5 Off-limits & 约束（哪些文件/模块不能动）
  - [ ] 3.6 文件级任务拆分（衔接 task-spec-gen）
- [ ] Step 4: 输出方案 Markdown
- [ ] Step 5: 用户确认 ⚠️ REQUIRED
  - [ ] 通过 → Step 6
  - [ ] 需修改 → 迭代回 Step 3/4
- [ ] Step 6: 写入学城 KM（conditional — 用户要求时）
- [ ] Step 7: 自检 Checklist
```

## Step 1: 理解需求 ⛔ BLOCKING

### 获取需求内容

| 来源 | 处理方式 |
|------|---------|
| KM 文档链接 | `oa-skills citadel getMarkdown --contentId <id> --mis <mis>` |
| 口述需求 | 直接使用描述文本 |
| GitHub Issue | `gh issue view <N> --json title,body` |

URL 解析：`km.sankuai.com/collabpage/2748397739` → `--contentId 2748397739`

### 确认目标仓库 ⚠️ REQUIRED

用户必须提供仓库本地路径。如果未提供，**立即询问**，不要猜测。

问："需求涉及哪个仓库？请提供本地路径。"

### 1.4 矛盾检测

识别需求中的隐含矛盾，发现后**主动提出**而非默默做取舍：

| 矛盾类型 | 示例 | 处理方式 |
|---------|------|---------|
| 性能 vs 依赖 | "不加新依赖" + "需要图表功能" | 问：是自己写还是用库？ |
| 时间 vs 范围 | "一周上线" + "支持三端兼容" | 建议分期 |
| 体验 vs 成本 | "离线使用" + "数据实时同步" | 需讨论权衡 |
| 灵活 vs 稳定 | "频繁变更" + "要稳定" | 建议配置化 + 功能开关 |

### 1.5 复杂度判定

根据需求特征判定方案复杂度，决定输出模板裁剪：

| 特征 | 精简版 | 标准版 | 完整版 |
|------|--------|--------|--------|
| 涉及文件数 | ≤3 | 4-8 | >8 |
| 预估工期 | ≤1 天 | 1-3 天 | >3 天 |
| 跨模块 | 否 | 轻微 | 是 |
| 新页面 | 否 | 部分 | 是 |
| 输出 | 一、三、五、六 | 大部分章节 | 全部章节 |

## Step 2: 深入分析代码 ⛔ BLOCKING

进入目标仓库后，按以下顺序分析。**每一步都要实际执行，不能跳过。**

### 2.1 项目概览

- 读 `package.json` → 确定技术栈、主要依赖、测试框架
- 读 `tsconfig.json` → TypeScript 配置、路径别名
- 读 `README.md` / `CLAUDE.md` → 项目约定
- `ls` 主要目录 → 理解项目分层（pages / components / api / store / hooks / utils 等）
- 识别样式体系：CSS Modules / styled-components / tailwind / less / scss

### 2.2 追踪入口链路 ⛔ MUST TRACE, NOT JUST SEARCH

从用户可见的入口开始，**逐层追踪到数据层**，不能只搜关键词就列文件：

1. **路由入口**: 找到 route 配置 → 确定页面组件路径
2. **页面组件**: 读完整组件代码 → 识别子组件、hooks、API 调用
3. **子组件链**: 递归追踪关键子组件（至少 2 层深度）
4. **数据流**:
   - 用户操作 → 事件处理函数 → API 调用 → 数据返回 → state 更新 → 重新渲染
   - **完整追踪这条链路，每一环都要读到具体代码**
5. **API 层**: 找到 service/api 文件 → 读请求函数 → 确认 URL、参数、返回类型
6. **状态管理**: 找到 store/context → 读 state 结构、action/reducer、selector

⛔ 禁止：
- 搜到文件名但没读内容就列入 "相关文件"
- 读了 export 但没读函数体就说 "理解了逻辑"
- 没有追踪到 API 层就声称 "分析了数据流"

### 2.3 深入阅读 + 寻找参考实现 ⚠️ CRITICAL

#### 目标代码精读

对每个要修改的文件，读取并记录：
- 完整的 TypeScript 类型/接口定义
- 关键函数的实现逻辑（不是函数签名）
- 组件的完整 props 定义 + 内部 state
- useEffect / useMemo / useCallback 的依赖数组和触发时机

#### 参考实现搜索

Ask: 代码库中有没有类似的功能已经实现了？

搜索策略：
- 需求是"加分页" → grep usePagination / Pagination / pageSize
- 需求是"新增表单页" → 找一个现有表单页，完整读一遍
- 需求是"对接新接口" → 找一个现有的 service 文件，读调用模式

找到参考后：
- **完整阅读参考实现的代码**（不是看标题就跳过）
- 记录："参考 `src/pages/OrderList` 的分页模式，它使用 useTable hook + antd Table"
- 方案中的实现必须与参考实现风格一致

### 2.4 影响范围分析（必须量化）

不是 "可能影响其他组件"，而是具体的文件和组件名：

1. **Grep 反向引用**: 搜索所有 import 了目标文件的文件 → 列出引用者
2. **类型传播**: 如果改了一个 interface，谁 extends/implements 它？
3. **Store 影响**: 如果改了 state 结构，哪些 selector/组件会受影响？
4. **路由影响**: 改了页面路径，哪些地方有 hardcode 的跳转？

输出格式（必须具体）：
- ✅ "修改 UserStore.userList 字段类型，影响 3 个组件：UserTable, UserCard, UserExport"
- ❌ "可能影响用户模块的其他组件"

### 2.5 前端特有维度分析

| 维度 | 分析什么 |
|------|---------|
| 组件树 | 改了这个组件，哪些父/子组件受影响？ |
| 状态管理 | 这个 state 在哪些页面共享？改了 store 谁会挂？ |
| 样式 | 用的哪套样式方案？改样式会不会影响其他页面？ |
| 构建 & 包体积 | 引入新依赖对 bundle size 的影响 |
| 端兼容 | PC / H5 / App WebView 差异处理 |
| UI 稿 | 有没有 Figma/Sketch 链接？交互细节在哪看？ |

### 2.6 分析结果确认 ⚠️ CHECKPOINT

分析完成后，**必须向用户汇报发现并确认**，不要直接进入 Step 3。

```
**代码分析结论：**
- 需要修改的文件：[列表]
- 参考实现：[路径 + 简述]
- 影响范围：[具体组件/页面]

**⚠️ 待确认项：**
- [不确定的点 1]
- [不确定的点 2]

确认后进入方案设计。
```

等用户确认后再进入 Step 3。

## Uncertainty Protocol

在分析和设计过程中，遇到以下情况**必须立即问用户**，不得自行假设：

### 🔴 必须立即问（STOP and ASK）

| 触发条件 | 示例 | 问法 |
|---------|------|------|
| 找不到相关代码 | 搜 pagination 无结果 | "代码库中没找到分页相关实现，是否有别的关键词？或者这是新功能？" |
| 接口信息不确定 | 不知道 API URL 和参数 | "后端接口的 URL、入参、返回值是什么？有文档链接吗？" |
| 需求有多种理解 | "优化列表" | "这里的'优化'指：A. 加载性能 B. 交互体验 C. 两者都要？" |
| 技术方案有取舍 | 改造 vs 新建 | "方案 A 改现有组件（小但受限），方案 B 新建（灵活但量大）。你倾向？" |
| 涉及其他团队 | 需要后端改接口 | "这个功能需要后端新增/修改接口吗？还是纯前端？" |
| 设计稿不明确 | 交互细节缺失 | "设计稿中列表空状态展示什么？加载用 skeleton 还是 spinner？" |

### 🟡 记录但继续（标注 ⚠️ 待确认）

| 触发条件 | 处理方式 |
|---------|---------|
| 有合理默认值 | 采用默认值，标注 "⚠️ 假设 pageSize=20，待确认" |
| 参考了现有实现 | 标注 "⚠️ 参考 OrderList 模式，如有特殊要求请告知" |
| 版本/兼容性不确定 | 标注 "⚠️ 假设不需要支持 IE" |

### ⛔ 绝对禁止

- 编造 API URL（如 `/api/v1/users/list`，代码中没有）
- 编造组件 props（没确认 Table 组件支持某个 prop）
- 编造 store 结构（实际 store 中没有某字段）
- 假设后端已做好接口（没看到代码/文档就说"调用后端分页接口"）

## Step 3: 设计方案

### 设计原则

1. **复用优先**：优先复用现有架构、组件、工具函数
2. **最小改动**：改动范围尽可能小，不做不必要的重构
3. **模式一致**：跟随仓库现有的编码风格和设计模式

### 方案选型（conditional）

有多种可行方案时，列出对比：
- 每种方案的实现思路
- 优缺点对比
- 选型结论和理由

### 详细设计

Ask: 拿到这份方案的研发同学，能否不需要额外沟通就开始编码？

必须包含：
- 每个改动文件的具体改动说明
- 新增/修改的数据结构（TypeScript 类型定义）
- 接口定义（URL、参数、响应、错误码）
- 关键交互逻辑的伪代码或流程描述

### 边界条件

Ask: 什么情况下这个功能会出问题？

逐一检查：
- 空数据 / 空列表 → 展示什么
- 加载中 → Skeleton / Spinner
- 网络错误 / 接口超时 → 提示 + 重试
- 权限不足 → 如何处理
- 并发操作 → 竞态条件
- 数据格式异常 → 容错

### 3.5 Off-limits & 约束

**必须填写**——这部分直接传递给 task-spec-gen 和子 Agent。

列出本次需求**不应该触碰的文件/模块**及原因，以及必须遵守的约束。

### 3.6 文件级任务拆分

按模板 6.1 的格式，拆到文件粒度。每个任务对应一组紧密相关的文件 + 测试。
标注任务间依赖关系。这个拆分直接供 task-spec-gen 消费。

## Step 4: 输出方案

加载 `references/techplan-template.md` 获取完整模板结构。

按模板输出 Markdown。关键规则：
- 根据 Step 1.5 的复杂度判定裁剪章节
- 第五章（模块详细设计）是**核心**，必须基于 Step 2 的代码分析
- 5.5 Off-limits **必须填写**
- 6.1 任务拆分必须到**文件粒度**
- 单方案时跳过第四章
- 不确定的信息用 `{待填写}` 标记，不要编造
- 数据结构用代码块展示

### 保存方案文件 ⚠️ REQUIRED

如果在编排器流程中调用（存在 `.clawdbot/` 目录），**必须将方案保存为文件**：

```bash
# 保存到 .clawdbot/{task_id}-techplan.md
# task-spec-gen 和 launch.sh 依赖这个文件
```

这不是可选步骤——不保存文件，下游 task-spec-gen 无法读取方案，launch.sh 无法复制到 worktree。

## Step 5: 用户确认 ⚠️ REQUIRED

输出方案后，**必须等用户确认**。

问："方案已输出，请确认：\n1. 通过，可以写入学城\n2. 需要修改（请说明哪里需要调整）\n3. 仅查看，不写入"

⚠️ 未经确认，不得写入 KM。

## Step 6: 写入学城（conditional）

用户确认通过且要求写入时：

```bash
oa-skills citadel createDocument \
  --title "【{端}】{需求名称}-技术方案" \
  --content "{markdown 内容}" \
  --mis {用户MIS}
```

可选参数：`--parentId <id>` 指定父文档。

写入成功后返回文档链接给用户。

## Step 7: 自检 Checklist

输出方案前，逐项自检：

### 代码粒度检查（原有）
- [ ] 第五章包含具体文件路径（不是"相关文件"）
- [ ] 数据结构有代码块展示
- [ ] 边界条件至少覆盖 3 种场景
- [ ] 不确定的信息用 `{待填写}` 标记而非编造
- [ ] 所有接口定义来自实际代码或后端文档
- [ ] 无残留的模板占位符（{页面名}、{功能点} 等）

### 架构级检查（v2 新增）
- [ ] 目标是否可验证（不是"优化体验"而是具体指标）
- [ ] 现状分析是否基于代码（而非凭经验猜测）
- [ ] 参考实现是否已找到并完整阅读
- [ ] 影响范围是否量化到具体组件/文件（不是"可能影响"）
- [ ] 5.5 Off-limits 是否已填写
- [ ] 6.1 任务拆分是否到文件粒度（不是"开发 3pd"）
- [ ] 新依赖是否评估了包体积影响
- [ ] 是否有回滚方案（标准版/完整版必须）
- [ ] 是否考虑了上线顺序（前端先发还是后端先发）

## 下游消费

本 SKILL 产出的技术方案被两个下游消费：

1. **task-spec-gen**：读取第五章 + 5.5 + 6.1，拆为 bite-sized Task Spec

如果在编排器流程中使用，方案应保存为 `.clawdbot/{task_id}-techplan.md`，
供 launch.sh 复制到 worktree。

## Anti-Patterns

- **空中楼阁**：没读代码就出方案，全是泛泛而谈（"修改相关文件"）
- **复制粘贴**：照搬模板占位符，没有填入实际内容
- **过度设计**：小需求写出大论文，引入不必要的抽象
- **遗漏边界**：只写 happy path，不考虑异常场景
- **编造接口**：猜测 URL 和参数，不基于实际代码或后端文档
- **模板教条**：生搬八个章节，实际只需要三个章节的小需求也全写
- **沉默假设**：遇到不确定的点不问用户，自己编一个"合理的"答案
- **浅尝辄止**：搜到文件名就列为"相关文件"，没有深入阅读理解

## Red Flags (return to Step 2 if any appear)

- 方案中出现 "修改相关文件" 而不是具体文件路径
- 数据结构是凭空想象而非从代码中提取
- 详细设计只有一两句话概括
- 没有任何代码引用或文件路径
- 没有参考实现（代码库中一定有类似的东西）
- 5.5 Off-limits 为空
- 6.1 任务拆分是 "开发 Xpd" 而不是文件列表
