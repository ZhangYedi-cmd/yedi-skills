# TechPlan Agent

IRON LAW: NO TECH PLAN WITHOUT READING THE ACTUAL CODE FIRST. 凭空想象的方案是废纸。

## Workflow

Copy this checklist and check off items as you complete them:

```
- [ ] Step 1: 理解需求 ⛔ BLOCKING
  - [ ] 1.1 获取需求内容（KM 链接 / 口述 / Issue）
  - [ ] 1.2 提取核心要求（改什么、为什么、影响谁）
  - [ ] 1.3 确认目标仓库路径 ⚠️ REQUIRED
- [ ] Step 2: 深入分析代码 ⛔ BLOCKING
  - [ ] 2.1 项目概览（技术栈、目录结构）
  - [ ] 2.2 定位相关文件（搜索关键词、追踪引用）
  - [ ] 2.3 读取核心代码（理解现有逻辑）
  - [ ] 2.4 分析依赖链（组件/接口/状态/路由）
  - [ ] 2.5 记录发现（改哪些文件、现有模式、影响范围）
- [ ] Step 3: 设计方案
  - [ ] 3.1 确定改动策略（复用现有模式，最小改动）
  - [ ] 3.2 多方案对比（conditional — 有多种可行方案时）
  - [ ] 3.3 详细设计（文件级改动 + 数据结构 + 交互逻辑）
  - [ ] 3.4 边界条件 & 异常处理
- [ ] Step 4: 输出方案 Markdown
- [ ] Step 5: 用户确认 ⚠️ REQUIRED
  - [ ] 通过 → Step 6
  - [ ] 需修改 → 迭代回 Step 3/4
- [ ] Step 6: 写入学城 KM（conditional — 用户要求时）
```

## Step 1: 理解需求 ⛔ BLOCKING

### 获取需求内容

| 来源 | 处理方式 |
|------|---------|
| KM 文档链接 | `oa-skills citadel getMarkdown --contentId <id> --mis <mis>` |
| 口述需求 | 直接使用描述文本 |
| GitHub Issue | `gh issue view <N> --json title,body` |

URL 解析：`km.sankuai.com/collabpage/2748397739` → `--contentId 2748397739`

### 确认目标仓库 ⚠️ REQUIRED

用户必须提供仓库本地路径。如果未提供，**立即询问**，不要猜测。

问："需求涉及哪个仓库？请提供本地路径。"

## Step 2: 深入分析代码 ⛔ BLOCKING

进入目标仓库后，按以下顺序分析。**每一步都要实际执行，不能跳过。**

### 2.1 项目概览

- 读 `package.json` / `pom.xml` / `go.mod` → 确定技术栈和依赖
- 读 `README.md` / `CLAUDE.md` → 了解项目约定
- `ls` 主要目录 → 理解项目分层（pages / components / api / store 等）

### 2.2 定位相关文件

根据需求关键词搜索：
- 页面/组件名
- 接口路径
- 路由配置
- 业务关键词

Ask: 在这个代码库中，需求描述的功能对应哪些文件？从路由入口开始追踪。

### 2.3 读取核心代码

读取定位到的文件，理解：
- 现有功能的实现逻辑
- 组件的 props 和状态
- 接口的调用方式和数据流
- 已有的设计模式（是否有类似功能可参考）

### 2.4 分析依赖链

Ask: 如果修改了定位到的文件，还有哪些地方会受影响？

- 组件间引用关系
- 接口调用链路
- 状态管理（Redux / MobX / Context / hooks）
- 路由配置

### 2.5 记录发现

整理代码分析结论：
- 需要修改的文件清单
- 现有代码使用的设计模式
- 可复用的现有组件/工具
- 潜在的影响范围

## Step 3: 设计方案

### 设计原则

1. **复用优先**：优先复用现有架构、组件、工具函数
2. **最小改动**：改动范围尽可能小，不做不必要的重构
3. **模式一致**：跟随仓库现有的编码风格和设计模式

### 方案选型（conditional）

有多种可行方案时，列出对比：
- 每种方案的实现思路
- 优缺点对比
- 选型结论和理由

### 详细设计

Ask: 拿到这份方案的研发同学，能否不需要额外沟通就开始编码？

必须包含：
- 每个改动文件的具体改动说明
- 新增/修改的数据结构（用项目语言的类型定义）
- 接口定义（URL、参数、响应、域名）
- 关键交互逻辑的伪代码或流程描述

### 边界条件

Ask: 什么情况下这个功能会出问题？

逐一检查：
- 空数据 / 空列表
- 网络错误 / 接口超时
- 权限不足
- 并发操作
- 数据格式异常

## Step 4: 输出方案

加载 `references/techplan-template.md` 获取完整模板结构。

按模板输出 Markdown。关键规则：
- 第五章（模块详细设计）是**核心**，必须基于 Step 2 的代码分析
- 单方案时跳过第四章
- 不确定的信息用 `{待填写}` 标记，不要编造
- 数据结构用代码块展示

## Step 5: 用户确认 ⚠️ REQUIRED

输出方案后，**必须等用户确认**。

问："方案已输出，请确认：\n1. 通过，可以写入学城\n2. 需要修改（请说明哪里需要调整）\n3. 仅查看，不写入"

⚠️ 未经确认，不得写入 KM。

## Step 6: 写入学城（conditional）

用户确认通过且要求写入时：

```bash
oa-skills citadel createDocument \
  --title "【{端}】{需求名称}-技术方案" \
  --content "{markdown 内容}" \
  --mis {用户MIS}
```

可选参数：`--parentId <id>` 指定父文档。

写入成功后返回文档链接给用户。

## Anti-Patterns

- **空中楼阁**：没读代码就出方案，全是泛泛而谈（"修改相关文件"）
- **复制粘贴**：照搬模板占位符，没有填入实际内容
- **过度设计**：小需求写出大论文，引入不必要的抽象
- **遗漏边界**：只写 happy path，不考虑异常场景
- **编造接口**：猜测 URL 和参数，不基于实际代码或后端文档
- **模板教条**：生搬八个章节，实际只需要三个章节的小需求也全写

## Red Flags (return to Step 2 if any appear)

- 方案中出现 "修改相关文件" 而不是具体文件路径
- 数据结构是凭空想象而非从代码中提取
- 详细设计只有一两句话概括
- 没有任何代码引用或文件路径

## Pre-Delivery Checklist

- [ ] 第五章包含具体文件路径（不是"相关文件"）
- [ ] 数据结构有代码块展示
- [ ] 边界条件至少覆盖 3 种场景
- [ ] 不确定的信息用 `{待填写}` 标记而非编造
- [ ] 所有接口定义来自实际代码或后端文档
- [ ] 任务拆分的估时合理（不是全填 1pd）
- [ ] 无残留的模板占位符（{页面名}、{功能点} 等）
