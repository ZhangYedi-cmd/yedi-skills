# 评审标准参考文档

本文档为 Reviewer Agent 提供评审时的标准化检查框架。所有评审以 spec.md 为最终依据，本文档仅作为检查流程的辅助参考。

---

## 1. 功能需求检查

### 1.1 验收标准逐条对照

对 spec.md 中该 task 的每条验收标准：

- 在代码变更中找到对应实现
- 确认实现逻辑与标准描述一致
- 确认没有遗漏的功能点

### 1.2 常见功能遗漏模式

| 遗漏类型 | 检查方法 |
|---|---|
| 只实现了正常路径，缺少错误处理 | 检查 Spec 是否要求错误处理；若要求，确认 catch/error path 存在 |
| 缺少边界条件处理 | 检查 Spec 是否指定边界行为；若指定，确认实现覆盖 |
| 功能实现但未暴露（缺少路由/导出） | 检查新功能是否在入口文件中注册 |
| 实现了但参数/返回值与 Spec 不符 | 对照 Spec 的接口契约逐字段验证 |

### 1.3 判定标准

- **PASS**：代码变更中存在对应实现，且逻辑正确
- **FAIL**：缺少实现、实现逻辑有明显错误、或与 Spec 描述不符

## 2. Spec 约束检查

### 2.1 禁止修改的文件

从 spec.md 的"风险与约束"段落中提取不能动的文件列表，逐一检查 diff 中是否包含这些文件的修改。

判定：
- diff 中不包含禁止文件 → PASS
- diff 中包含禁止文件 → FAIL（即使修改看起来"合理"也不能通过，因为这是硬性约束）

### 2.2 接口契约

从 spec.md 中提取接口契约定义（函数签名、API 路径、请求/响应格式、数据结构），检查实现是否严格遵守。

判定：
- 完全遵守 → PASS
- 偏离契约（如改了参数名、改了返回结构） → FAIL

### 2.3 跨任务冲突

检查该 task 的变更是否触碰了其他 task 的领地（根据 spec.md 的任务拆分信息判断）。

判定：
- 变更范围在该 task 职责内 → PASS
- 修改了明确属于其他 task 的文件或逻辑 → FAIL

## 3. 安全与技术债检查

### 3.1 安全风险

| 风险类型 | 检查方法 |
|---|---|
| 硬编码密钥/密码 | 搜索 diff 中的字符串常量，检查是否包含 API key、password、secret 等 |
| SQL 注入 | 检查是否有字符串拼接 SQL 而非参数化查询 |
| 路径遍历 | 检查文件操作是否验证路径输入 |
| 不安全的依赖 | 检查新增依赖是否来自可信来源 |

### 3.2 技术债

| 债务类型 | 检查方法 |
|---|---|
| 大量 TODO/FIXME | 统计 diff 中新增的 TODO/FIXME 数量，与 Spec 中的已知遗留对照 |
| 重复代码 | 检查是否有明显的复制粘贴代码块 |
| 过度硬编码 | 检查是否有应该配置化但被硬编码的值 |

### 3.3 判定标准

**重要**：安全与技术债检查遵循"只认 Spec"原则：

- 若 Spec 验收标准中包含安全/质量要求 → 该项检查结果影响 verdict
- 若 Spec 未提及 → 在报告中记录为"额外观察"，**不影响 verdict**
- 例外：明显的安全漏洞（硬编码密码等）即使 Spec 未提及，也应标注为 FAIL 并说明理由

## 4. 不确定项处理

### 4.1 识别不确定项

从 spec.md 的"不确定项"区块中提取所有条目。这些是规划师在静态分析阶段无法确认的内容，Worker 在执行时有自主判断空间。

### 4.2 评审态度

对于不确定项相关的实现：

- Worker 选择了合理的处理方式，且不违反 Spec 硬性约束 → **不打回**
- Worker 选择了与 Reviewer 预期不同但逻辑自洽的方式 → **不打回**，在报告中记录观察
- Worker 的处理方式导致违反了 Spec 硬性约束 → **打回**，但明确说明是约束违反而非不确定项本身的问题

### 4.3 判定标准

- 不确定项本身**永远不是打回的理由**
- 只有当不确定项的处理方式**间接导致了硬性约束违反**时，才会因约束违反而打回

## 5. Spec 错误识别

### 5.1 什么是 Spec 错误

| 类型 | 示例 |
|---|---|
| 引用不存在的接口 | Spec 要求调用 `UserService.get_by_id()` 但该方法不存在 |
| 内部矛盾 | Spec A 处说"使用 REST API"，B 处说"使用 GraphQL" |
| 技术不可行 | Spec 要求的实现方式在当前框架版本中不支持 |
| 依赖错误 | Spec 假设 task-A 会提供某接口，但 task-A 的 Spec 中无此内容 |

### 5.2 什么不是 Spec 错误

| 情况 | 正确处理 |
|---|---|
| Worker 能力不足导致实现不了 | verdict: fail，不标注 spec_error |
| Worker 误解了 Spec 的意思 | verdict: fail，在修改方向中澄清正确理解 |
| 实现有 bug | verdict: fail，指出 bug 位置和修复方向 |

### 5.3 标注规则

- 在报告 frontmatter 中设置 `spec_error: true`
- verdict 仍为 `fail`
- 在报告的"Spec 错误"区块详细说明问题、依据和建议
- 包工头会据此决定是否发起 Spec Amendment 流程

## 6. 大体量 Diff 的评审策略

当 diff 超过 5000 行时，采用分层评审策略：

### 优先级 1（必须全量审查）

- Spec 直接提及的文件
- 包含接口契约定义的文件
- 入口文件、配置文件

### 优先级 2（抽样审查）

- 工具类/辅助函数文件
- 测试文件
- 样式/模板文件

### 优先级 3（仅检查存在性）

- 静态资源
- 自动生成的文件

在报告中注明实际审查覆盖范围，标注哪些文件仅做了抽样检查。
