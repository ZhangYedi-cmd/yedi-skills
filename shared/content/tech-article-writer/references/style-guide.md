# 风格规范（提炼自《AI Coding 实战》系列 5.1 项目初始化 / 5.2 接口契约 / 5.3 后端实现）

写正文前通读本文件。所有示例均摘自原系列，是"照着写"的样板，不是参考建议。

## 1. 整体气质

- 教程式实战文，读者是要**跟着做一遍**的工程师，不是来看观点的
- 工程口吻，平实、克制、信息密度高；不煽情、不堆背景、不写"在当今时代"式空话
- 每个决策都给理由，先讲为什么再讲怎么做——读者照做之余能带走判断力
- 诚实标注边界："本节不展开""这里只需要知道 X，对齐工作放到下一节做"

## 2. 文章骨架

```
[引言 2-3 段，无标题]
  段1：承接上文——上一篇结束时达到了什么状态（具体、可验证）
  段2：但还差什么——现在动手会遇到什么问题（给具体失败场景）
  段3："这一节的任务是…" + 结束状态清单
## 一、为什么 XXX（动机章）
### 1.1 根本问题
### 1.2 (可选)额外价值
### 1.3 整体工作流  ← 第一张 mermaid 图放这
## 二、主体章（怎么做）
### 2.1 …
## 三、主体章
…
## N、验证/验收
## N+1、小结（可合并进验证章）
  决策回顾 + 关键产出文件清单 + 下一篇承接
```

标题风格：一级标题用「一、二、三」中文序号（步骤强顺序的文章也可用「第一步：」「第二步：」），二级标题用 1.1/2.1 数字编号。标题是短语不是句子："先列清单，再动手"、"从 Schema 到 TypeScript"。

## 3. 引言样板（三段式，逐段对照）

承接段：
> 5.1 节结束时，项目骨架已经跑起来了：`pnpm dev` 能起、`tsc --noEmit` 通过、四个基础设施的健康检查都返回 OK。但此时前端和后端仍然处于"两侧互不知道对方长什么样"的状态……

缺口段（具体失败场景 + 代价）：
> 如果现在就开始写 UI 或后端实现，两侧会在各自对接口的假设下快速积累代码。等到联调时，字段名不一致、错误格式不统一……每一处分歧都意味着需要同时改前端和后端——代价随代码量线性增长。

任务段（任务 + 做完后的状态）：
> 这一节的任务是在实现开始之前，把接口契约立起来。契约立好之后，前端对着 Mock 独立开发，后端对着 schema 独立实现，两侧联调时切换一个环境变量就完成对接。

无系列上下文时，承接段改为现状/痛点开场，其余不变。

## 4. 措辞规则（硬约束）

1. **破折号做因果/解释**，高频使用："——所以第一次就要对"、"——这是后续所有 diff 的基点"
2. **决策句式**："这里推荐 X。原因有两个：一是…；二是…"、"X 有几个主流选择：A 侧重…，B 功能最全但…，C 则是最轻量的——这里推荐 C"
3. **量化代价与收益**，不用"很慢/很快"："百万条向量没有索引时，一次余弦检索耗时可达秒级，加了 HNSW 索引后降至几毫秒"
4. **预警句式**："这里有一个坑需要提前说明"、"最后这步不要跳过——X 在写入时才会报错，定位起来很绕，不如在这里提前确认"
5. **审查句式**："生成后人工审查两个重点。第一是…。第二是…"、"收到清单后，重点检查两类遗漏"
6. **概念解释**：面向不熟悉该领域的读者，术语首次出现给一句话解释 + 一个直觉类比："把每个向量想象成从原点出发的一根箭头，两根箭头指向越接近同一个方向，余弦相似度越接近 1"；并明确降低负担："这两个概念不需要深入理解，只需要知道建表时必须正确配置"
7. **给判断不含糊**："这不是谁的失误，而是约定本身没有任何机制保证它被遵守"；该下结论就下
8. **克制的完美主义**："这一步不用追求完整，大差不差即可——schema 不是一次性产物"
9. 禁：黑话堆砌、感叹号、"让我们"、"值得一提的是"滥用、每段都以"首先/其次"开头

## 5. 代码块的四种角色

| 角色 | 语言标注 | 规则 |
| --- | --- | --- |
| 喂给 AI/CC 的 prompt | ```plain | 命令式写，先"读取 X 文档"，再列要求（编号列表），结尾给约束（"不要引入文档里没有的分层"）。prompt 本身就是教学内容 |
| 验证命令 | ```bash | 每条带行内注释说明预期（`pnpm tsc --noEmit   # strict mode 已生效（空项目 0 错误）`） |
| 参考实现/产物示例 | ```typescript/yaml/sql/json | 只放核心片段，首行注释标文件路径（`// packages/web/src/mocks/handlers/chat.ts`），可加"（自动生成，不要手改）"类标注 |
| 目录结构 | ```plain | tree 风格，每行尾注释职责 |

代码前必有引出句（"生成的 handler 大概长这样："），代码后如有审查点必须写出来。

## 6. mermaid 图规范

- 嵌入 ```mermaid 源码块（语雀等平台会渲染成 SVG）
- 位置：动机章末尾的"整体思路/工作流"小节，或主体章开头的"链路总览"
- 图前一句引出："整条问答链路的数据流大致如下："
- 图后一段解读，讲图上看不出来的约束："这四步有严格的顺序依赖：目录结构要在基础设施接入之前确定，因为…"
- flowchart 节点文字用短语；sequenceDiagram 参与方按真实模块命名（前端 useChat / API Route / 向量库 / LLM）
- 需要截图的操作步骤用占位注释标出，不假装有图：`<!-- screenshot: SQL Editor 执行成功的界面 -->`

## 7. 验证闭环（本风格的灵魂）

- 每个主体章以"怎么确认这步成了"收尾，验证方式必须具体可执行：一条 curl、一个 ts-node 脚本、Dashboard 上看哪个列表
- 给预期输出的样子，不只给命令：
> 正常运行时，终端会看到逐行输出的 Vercel AI SDK 数据流格式，类似：`0:"这"` … 看到这个格式说明流式接口工作正常。
- 收尾章给验证清单表格：

```markdown
| 接口 / 模块 | 验证方式 | 预期结果 |
| --- | --- | --- |
| `searchSimilarChunks` | ts-node 测试脚本 | 返回语义相关的 chunks |
| `POST /api/chat` | curl -N | 看到逐行 `0:"..."` 输出 |
```

- 引言的验收标准和收尾清单要能对上——引言承诺什么，结尾验证什么

## 8. 收尾样板

小结三件事：决策回顾（"实现过程中有几个决策值得记住：…"）、关键产出文件清单（`+` 列表，路径 + 一句话）、下一篇承接（"5.4 节开始做组件开发……随时可以把 `VITE_USE_MSW` 改为 `false` 切换到真实接口联调"）。

无下一篇时，承接段改为"从这里往下走"：读者接下来自然会遇到的 2-3 个方向，各一句话。

## 9. 引用与数据红线

- 外部数据（市场份额、benchmark 分数）必须带来源链接，行内 Markdown 链接：`[46%](https://...)`
- 版本敏感的 API 写明基于哪个版本，并说明相邻版本差异（参考 5.3 对 Vercel AI SDK v3/v4/v5 的处理）
- 素材里没有的数字一律不编；不确定的写"以官方文档为准"并给链接
