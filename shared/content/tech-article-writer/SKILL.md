# 技术分享文章写作

把输入素材加工成一篇「教程式技术分享文章」，目标读者是想跟着做一遍的工程师。
风格规范全文见 [references/style-guide.md](references/style-guide.md)，写正文前必读。

## 输入

用户可能给的素材（有多少收多少，不强求全）：

- 主题 / 要解决的问题（必需，没有就问）
- 目标读者（默认：前端/全栈工程师，具备基础但不熟悉本文主题）
- 系列上下文：上一篇讲了什么、下一篇要讲什么（决定引言和结尾的承接写法）
- 原始素材：代码片段、操作记录、聊天记录、大纲、参考链接
- 篇幅预期（默认 3000-6000 字正文）

**只在主题或核心素材缺失时提问，一次问完。** 素材够了直接进入拆章节。

## 工作流

### Step 1：拆章节（先出大纲，用户确认后再写正文）

产出一份大纲，结构固定为：

1. **引言**（无标题，2-3 段）：承接上文 → 指出当前缺口 → 本文任务 + 结束状态（可验证的验收标准）
2. **动机章**（为什么）：问题的根因分析，为什么要用本文的方案。放第一张 mermaid 总览图
3. **主体章 ×2-4**（怎么做）：按依赖顺序排列，每章 = 一个可独立验证的里程碑
4. **收尾章**：验证清单表格 + 小结 + 「下一步」承接下一篇

大纲里每章标注三件事：

- 一句话讲什么
- 配什么图（mermaid 类型 + 图要表达什么，见 Step 2 选型规则；没必要配图就写"无"）
- 放什么代码块（prompt / 参考实现 / 验证命令）

把大纲发给用户确认。用户说"直接写"或明显是自动化调用时跳过确认。

### Step 2：配图表（mermaid 源码直接嵌入正文）

选型规则（一篇文章 1-4 张图，宁缺毋滥）：

| 要表达的内容 | 图表类型 |
| --- | --- |
| 步骤依赖 / 工作流 / 推进顺序 | `flowchart LR` 或 `TD` |
| 模块分层 / 依赖关系（哪层先建） | `flowchart TD` + subgraph |
| 请求-响应数据流（多方参与、有时序） | `sequenceDiagram` |
| 多方案对比 / 现状数据 | Markdown 表格，不用 mermaid |

图的位置固定在「整体思路 / 链路总览」段落之后，正文先用一句话引出（"整条链路的数据流大致如下："），图后必须有一段文字解读图里的关键约束（顺序为什么不能乱、哪条边是重点）。图不自解释，文字才是主体。

### Step 3：写正文

逐章写，严格遵守 style-guide 的措辞规范。每个操作型章节的骨架：

1. **为什么**：这一步解决什么问题，不做会怎样（1-2 段，给具体的失败场景）
2. **怎么做**：具体操作。如果是 AI Coding 类文章，给出喂给 CC 的 prompt（```plain 代码块）；否则给命令/代码
3. **产物长什么样**：关键生成物的参考片段（```typescript/yaml/sql 等），只放核心部分
4. **人工审查点 / 坑**：明确列出"生成后重点检查 X 和 Y"，已知的坑提前说（"这里有一个坑需要提前说明"）
5. **验证**：一条能跑的命令 + 预期输出，确认通过再进下一步

不是每章五件事都要齐，但 **为什么 + 怎么做 + 验证** 三件缺一不可。

### Step 4：组装输出

- 输出单个 `.md` 文件，文件名 `<主题短语>.md`，写到用户指定目录（没指定就问一句或放当前目录）
- 自查清单（不过关就改，不发给用户半成品）：
  - [ ] 引言无标题、以承接或问题开场、末段有"本文/这一节的任务是…"+ 验收标准
  - [ ] 每个主体章都有验证入口，验证命令可直接复制执行
  - [ ] mermaid 图前有引出句、图后有解读段
  - [ ] 收尾有验证清单表格（模块 | 验证方式 | 预期结果）和下一步承接
  - [ ] 无凭空捏造的数据/benchmark；引用外部数据带来源链接
  - [ ] 通读一遍：措辞符合 style-guide（破折号因果、先为什么后怎么做、给判断不含糊）

## 边界

- 只产 Markdown 文章，不负责发布（发布用 baoyu-post-to-wechat 等 skill 另行处理）
- 图表只产 mermaid 源码，不渲染成图片（语雀/大部分平台原生渲染；需要 SVG 时另调 baoyu-diagram）
- 技术结论要可溯源：素材里没有的数字不编，不确定的写"以官方文档为准"并给链接
